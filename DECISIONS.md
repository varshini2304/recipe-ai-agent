# Decisions

| Decision | Alternatives considered | Reason |
|---|---|---|
| Preserve every source record and identify it as `{source}:{original_key}`. | Drop incomplete rows or deduplicate titles. | Missing content is useful to report, source IDs are stable, and same-title recipes can differ. |
| Keep source values in `*_raw` fields and store cleaned values separately. | Overwrite raw text during cleanup. | Auditable normalization and exact source preservation. |
| Use the source key's stripped, case-folded title to assign `title_dup_group`; never use it as a recipe ID. | Merge same-title recipes. | Duplicate title does not establish recipe identity. |
| Define usable ingredients as a nonempty list containing at least one nonblank string. | Count all records or require every line to parse. | Ingredient-based percentages need a consistent, reproducible denominator without excluding imperfect lines. |
| Set quality flags from nonblank cleaned title, at least one nonblank ingredient after configured scrape-noise cleanup, and nonblank cleaned instructions. | Treat any present JSON key as usable. | The flags represent whether the fields can support downstream use; missing/empty distinctions remain visible in the raw columns and report. |
| Define instruction steps as nonblank newline blocks, dropping configured boilerplate; use sentence splitting only if there is one nonblank block. | Count every sentence or line unconditionally. | Recipe instructions are commonly step-per-line, but some sources provide one paragraph. |
| Parse ingredients with a readable regex fallback. | `ingredient-parser-nlp`. | Neither `ingredient_parser` nor `ingredient_parser_nlp` is installed in this environment; regex behavior is explicit and testable. |
| Load object records incrementally with `ijson.kvitems`. | `json.load` for each 40–94 MB file. | Streaming meets the ingestion requirement and limits memory use. |
| Keep normalization merges in `config/synonyms.yaml` and log each applied merge. | Inline synonym maps. | Every canonical merge must be reviewable and adjustable without code edits. |
| Declare `faiss-cpu` as a dependency and verify its import before completing Phase 1. | Silently substitute another index. | The requested dependency must be checked explicitly on this Windows machine. |
| Scope duplicate-title groups to a source file and normalize title with trim plus case-fold only. | Group same titles across source files or collapse internal whitespace. | This reproduces per-source inspection counts and avoids inferring that same-title records from different providers are duplicates. |
| Record every plural and synonym canonicalization at INFO level in `data/normalization.log` during scripted ingestion. | Rely only on summary counts or enable logging ad hoc. | The requested audit trail should identify the raw-to-canonical merge for each affected ingredient line. |
| Keep `faiss-cpu` declared although its native module is blocked by Windows Application Control in this environment. | Replace it silently with numpy or another index. | Installation succeeded, but `import faiss` failed due an OS policy; Phase 1 records the failure and leaves retrieval implementation to a reviewed fallback choice. |
| Use the NumPy normalized-vector backend by default; keep FAISS optional and gated on successful import. | Use FAISS as default or switch backends silently. | Windows Application Control blocks the FAISS native module; NumPy cosine scoring is deterministic and keeps exact filtered top-k behavior. |
| Use the owner-approved starter taxonomy in `config/taxonomy.yaml`. | Apply unreviewed allergen/diet patterns. | Owner approved the generated taxonomy draft on 2026-11-11 before search/tests apply it. |
| Embed title plus the ordered canonical ingredient text with the configured MiniLM model; persist normalized float32 vectors and stable recipe IDs. | Embed raw lines or title only; use unnormalized Euclidean distance. | Canonical ingredient text matches the search document used by FTS, while exact IDs and cosine scores are reproducible. |
| Keep the first saved index limited to 5,000 deterministic searchable rows and retain the FTS index over all 122,971 eligible rows. | Build the full embedding matrix immediately. | The user asked for a timed development build and will decide when to spend time on a full vector build. |
| Select limited development subsets by interleaving source-local key order. | Take the first N rows from one lexicographically sorted source. | A quick index should contain recipes from all three sources while remaining deterministic. |
| Store FTS5 as a separate recipe-ID/title/canonical-ingredients side index and rebuild it after data ingestion. | Rebuild the 800 MB source database to add search text columns. | It keeps Phase 1 raw rows and ingredient lines intact while providing BM25 text search. |
| Use the final stratified 159.17-second 5,000-row run to estimate about 65m 15s for 122,971 rows. | Guess runtime from the model card or build the full corpus. | The estimate is a direct linear extrapolation from the actual final local run, not a promise of exact runtime. |
| Ingredient containment reports use usable-ingredient recipes (122,971) as primary denominator and include all recipes (125,164) as a secondary denominator. | Divide ingredient matches by every source record only. | The usable base is the meaningful population for ingredient containment; exposing both counts prevents denominator ambiguity. |
| Keep `match_mode` explicit (`exact` or reviewed `family`) in every ingredient filter and report matched canonical variants. | Silently expand singular ingredient terms to all token-containing names. | Product distinctions such as garlic powder must be explicit and auditable. Family rules in `config/families.yaml` were reviewed and approved by the owner on 2026-11-11. |
| Rank recipe steps by requested step direction, then ingredient_count ascending, then recipe_id ascending; report all recipes tied on cutoff step_count. | Reverse the whole ordering for descending steps or use recipe ID alone for ties. | A stable, intuitive tie break keeps simpler recipes first and exposes cutoff ties without ranking tricks. |
| Validate ingredient token counts with regex over raw JSON ingredient lines alongside canonical exact counts. | Treat canonical token-family union as raw-text ground truth. | Canonical synonyms and parser normalization can add or remove literal token mentions; both numbers and their gap are useful evidence. |
| For reviewed ingredient families, test patterns against the ingredient head before the first preparation comma. | Match a token anywhere in a canonical string. | Free-text notes inside ingredient lines can mention an ingredient without naming it as the line's product; head matching reduces false family matches while preserving preparation suffixes. |
| Exclude `tomatillo` from the tomato family. | Include any canonical line mentioning tomato, including tomatillo descriptions. | Canonical inspection found recipe text describing tomatillos as green tomatoes; these are a distinct product, and the owner approved the exclusion on 2026-11-11. |
| Keep `step_count` and add `sentence_count` as separate deterministic instruction metrics. | Infer one measure from the other. | Newline-block steps and sentence-like units answer different ranking questions; the sentence boundary and boilerplate rules are explicit in `config/steps.yaml`. |
| Flag instruction confidence when cleaned text is shorter than the configured minimum or has fewer than the configured count of configured action-like words. Exclude flagged candidates from fewest-metric rankings by default. | Treat every scraped instruction string as equally trustworthy. | The dataset includes short fragments and ingredient lists in the instructions field; ranking should surface plausible directions first and report both flagged and excluded candidate counts. |
| Use `step_count` as the default filter/ranking metric; allow `sentence_count` by `Filter.step_metric` and CLI option. | Make sentence count the default or expose two unrelated APIs. | The existing assignment question asks for recipe steps, while users can explicitly request sentence-based behavior. |
| Default user-facing ingredient containment to reviewed family mode; exact canonical equality remains an explicit option. | Keep exact as the default after observing large undercounts. | The assignment intent is ingredient presence across descriptive canonical variants, and the approved family rules preserve product distinctions. |
| Mark real full-database tests `slow`, exclude them from default pytest, and provide an all-tests target. | Make every local test run scan the 125,164-row dataset and vector index. | Fast unit feedback is useful during development while `make test-all` retains the full integration checks. |
| Compare family matches with literal raw token regex matches and select at most 30 examples per side with the seed in `config/gap_audit.yaml`. | Sample nondeterministically or fabricate a symmetric sample when one side is empty. | Reproducible samples make mismatches auditable; some set differences are empty or contain fewer than 30 recipes and are reported at their actual size. |
| Ignore downloaded `data_raw/` files, generated SQLite/index artifacts, and normalization logs. | Track large inputs and machine-specific derived data in source control. | These are reproducible/generated local artifacts; reports, code, schema, and configuration remain trackable. |
| Ignore local Salesforce `.sf/` metadata. | Commit org-specific CLI catalog state with the application source. | It is local tooling state and contains an organization identifier, not RecipeLens source. |
| Separate "green onion" (scallions, spring onions) into its own ingredient family, distinct from standard bulb onions. | Group green onions under the onion family or treat them as exact matches only. | Green onions/scallions possess a distinct flavor profile, culinary role (often fresh garnish), and substitution behavior compared to standard bulb onions (yellow/white/red), preventing unwanted cross-matches. |
| Allow explicit product forms (e.g. tomato sauce, garlic powder) to match when explicitly requested by name, while preserving base family product exclusions. | Strictly exclude all product forms from family containment even when specifically named, or conflate products with raw ingredients. | When a user requests "tomato sauce" or has "garlic powder" in their pantry, they specifically intend to match that product; conversely, querying base "tomato" or having fresh "garlic" must not match processed sauces or powders. |
| Expand reviewed family head patterns in `config/families.yaml` to include cut descriptors (`slice`, `wedge`, `halve`) and parentheticals rather than re-ingesting the corpus. | Force full database re-ingestion with broader comma-splitting regex or keep cut forms excluded. | Trailing-prep audit showed that true trailing prep verbs are already stripped by `prep_pattern`; the vast majority of remaining comma canonicals are either intentional product exclusions or minor cut descriptors (slices/wedges), making config-driven pattern coverage cleaner, zero-downtime, and auditable. |
| Preserve conjunctive compound lines (e.g. "salt and garlic powder", "salt and freshly ground black pepper") as single canonical strings. | Split conjunctive lines into synthetic separate ingredient rows. | Preserving source line unity avoids inventing synthetic recipe positions or fabricating quantities/units across conjunctive items; users matching exact canonicals match the compound directly, while family matching targets individual heads. |
| Use a frozen slotted `QueryPlan` dataclass with strictly enumerated intents and tuple slots. | Mutable dictionary or Pydantic model. | Dataclasses with slots ensure immutability, type safety, low memory overhead, and consistency with the rest of the recipelens store and service models without external Pydantic dependencies. |
| Maintain conversational session state as an immutable `SessionState` where follow-ups are deltas that never drop hard constraints. | Mutating a global dictionary or session object in place. | Immutable state transitions make session evolution pure and testable, prevent accidental filter loss across turns, and cleanly produce serializable constraint chips for downstream UI/CLI. |
| Implement a config-driven rule-based intent parser backed by an `IntentParser` protocol before adding LLMs. | Direct hardcoded if/else branching or mandatory LLM prompting. | A protocol abstraction allows zero-dependency deterministic testing and instant CLI execution, while keeping the interface cleanly swappable for Gemini/LLM parsers in later phases without altering the orchestrator router or state. |
| Route execution through a centralized `Router` returning a unified `ToolResult` container with explicit filters and metadata. | Direct ad-hoc execution across services in chat loops. | Centralized dispatch ensures that active filters and hard constraints from the session state are always applied consistently across hybrid search, analytics, and matcher services without dropping allergen or step constraints. |
| Use deterministic string template composition for user responses in Phase 4A without calling an LLM. | Generating responses via LLM prompts. | Eliminates hallucinations, produces auditable math and grounding, guarantees that cited recipe IDs and statistical denominators exactly match the database, and provides the baseline ground truth required for Phase 4B LLM evaluation. |
| Verify response grounding by extracting cited recipe IDs and cross-checking them against ToolResult candidates. | Relying on post-hoc prompt assertions or unverified text. | Explicit extraction and membership checking flags ungrounded recipe citations and fabricated IDs deterministically, providing safety gates before exposing answers to users or LLM eval loops. |
| Implement a unified `ChatSession` coordinator and replayable CLI tool supporting interactive REPL and scripted turns. | Hardcoding chat loops in standalone scripts without a reusable engine class. | A centralized `ChatSession` allows programmatic script replay for demo generation, regression testing, and future API/Web interfaces to reuse identical conversational mechanics. |
| Separate fast mock/fixture tests from full-corpus real-DB integration tests in `test_orchestrator.py`. | Running the entire 122,971-row search index on every test invocation. | Fast synthetic tests validate complex conversation state merges, intent edge cases, and grounding checks in seconds, while `@pytest.mark.slow` reserves full database integration for release verification. |
| Ground answer recipe IDs and numeric claims against service results; show original ingredient lines with search results. | Trust rendered templates or return semantic matches without evidence. | Deterministic checks catch fabricated IDs/numbers, and raw ingredient lines make search evidence auditable. |
| Cache taxonomy canonical IDs by group and uncertainty setting for the repository instance. | Rescan all distinct canonicals for each conversational refinement. | Repeated hard-constraint filters should reuse the same deterministic group expansion while each chat still creates a fresh repository-scoped cache. |
| Mine substitute candidates from same-dish peers using with/without recipe frequencies, smoothed rate differences, and lift; grade results only from configured support/effect thresholds. | Use a model to invent ingredient replacements or treat one co-occurrence as proof. | Recipe Box contains ingredient lists but no validated substitution labels, so results remain association evidence with counts, IDs, and uncertainty. |
| Use the full vector index for peer retrieval only when metadata confirms full corpus coverage; otherwise use FTS5 over the database. | Treat a 5,000-row dev vector subset as complete peer coverage. | This workspace has 122,971 vectors (188,883,584 bytes); fresh clones omit ignored local data/index artifacts, and the service reports its actual retrieval backend. |
| Preserve original ingredients/instructions and produce only annotated text edits; source predicted effects and disclaimers from `config/roles.yaml`. | Rewrite recipe quantities or claim tested results/medical safety. | The corpus does not validate adaptations or quantities; users need clear separation between dataset associations and general, unverified culinary expectations. |
| Evaluate Stage 4 cases through the real `ChatSession` while exposing its last structured plan, tool result, and verifier output for tests. | Reconstruct tool behavior from answer prose alone. | Structured results make each check machine-readable while the user-facing response remains the exact pipeline output. |
| Establish Stage 4 ingredient and ranking ground truth from pandas aggregation of original `ingredient_lines.raw` plus configured raw-text regexes; never use the canonical DB column as the evaluator's expected value. | Validate analytics against the same normalized canonical values they consume. | Independent inputs can reveal normalization drift. The run found a three-recipe garlic/onion discrepancy, which is preserved as a failure in `EVAL.md`. |
| Keep Gemini's no-tools baseline optional, cached, and explicitly uncollected when no API key is present. | Invent a sample model answer or make the evaluation depend on an external key. | No `GEMINI_API_KEY` was available in the environment or `.env`; `eval/oneshot_example.md` provides a manual slot and the configured SDK path for a future real call. |
| Document only currently runnable components and label the API/web directories as placeholders. | Describe planned UI/API behavior as implemented. | There is a runnable chat CLI in `scripts/chat.py`, but no API or web application module exists yet. |
| Explain that the downloaded Recipe Box archive carries ODC-By for the database and that scraped recipe content may have separate rights. | State a broader license claim for all recipe content. | The local archive's `LICENSE` is the Open Data Commons Attribution License; source-page recipe content can have rights beyond that database license. |
| Keep raw data, generated databases/indexes, local caches, and credentials outside Git; verify from tracked paths on the fresh-clone check. | Commit local runtime artifacts to make a clone appear preloaded. | A clean clone should reproduce setup and fast tests without private keys or multi-gigabyte local data artifacts. |
| Remove the tracked `apply_matcher_changes.py` helper during Stage 5 cleanup. | Leave a scratch patch script in the final submission. | It is a one-off edit helper, not part of the application or its reproducible workflow. |
